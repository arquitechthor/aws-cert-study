AWS Private CA

AWS Private Certificate Authority (AWS Private CA)

En una frase: Emite certificados privados para identificar servidores, dispositivos y servicios internos
Categoría: Seguridad, identidad y cumplimiento (Security, Identity, and Compliance)
Certificaciones: DVA-C03
Documentación oficial: Documentación de AWS Private CA ↗

Qué es

AWS Private CA (Private Certificate Authority) crea y gestiona autoridades de certificación privadas, con su jerarquía de CA raíz y subordinadas, sin montar ni mantener una PKI (Public Key Infrastructure: infraestructura de clave pública: autoridades, certificados y sus reglas) propia. Sus CA emiten certificados privados en los que solo confían tus sistemas: para cifrar con TLS (Transport Layer Security: cifrado de las conexiones) las comunicaciones internas, identificar servidores, contenedores, dispositivos y usuarios, o firmar código.

Conceptos clave

  • Jerarquía de CA: una CA raíz (la base de la confianza, que se usa lo mínimo) firma una o varias CA subordinadas, que son las que emiten los certificados del día a día.
  • Modo de uso: uso general (certificados con cualquier validez) o certificados de corta duración (siete días como máximo, más baratos y pensados para no necesitar revocación, por ejemplo para TLS mutuo entre servicios).
  • Revocación: la CA publica una CRL (Certificate Revocation List: lista de certificados revocados que publica una autoridad de certificación) en un depósito de S3 (Simple Storage Service) o responde por OCSP (Online Certificate Status Protocol: protocolo para consultar al momento si un certificado está revocado) para que los clientes sepan qué certificados ya no valen.
  • Integración con ACM (AWS Certificate Manager): ACM puede pedir certificados privados firmados por tu CA y renovarlos solo para usarlos en balanceadores, CloudFront o API Gateway. Para instalarlos en otro sitio, se exportan desde ACM o se emiten con la API (Application Programming Interface: interfaz para que los programas se comuniquen) de Private CA a partir de una CSR (Certificate Signing Request: solicitud de firma de un certificado).
  • Plantillas de certificado: definen el tipo de certificado que se emite (servidor, cliente, firma de código, CA subordinada…).
  • Compartir con RAM (Resource Access Manager): otras cuentas de la organización pueden emitir certificados con una CA central sin tener permisos sobre ella.
  • Regional: cada CA vive en una región; para otra región hay que crear otra CA (no se copian).
  • Algoritmos: RSA (Rivest-Shamir-Adleman: algoritmo de clave pública) y ECDSA, y también algoritmos de firma poscuánticos.

Casos de uso típicos

  • HTTPS (HTTP Secure: HTTP cifrado con TLS) dentro de la empresa (APIs internas, balanceadores internos) sin certificados públicos.
  • TLS mutuo entre microservicios o pods de EKS (Elastic Kubernetes Service), con certificados de corta duración.
  • Identidad de dispositivos de IoT (Internet of Things: internet de las cosas: dispositivos conectados) y de equipos corporativos.
  • Firma de código y de artefactos internos.
  • Sustituir una PKI local (por ejemplo, Microsoft AD CS) que cuesta mantener.

Cuándo NO usarlo

  • Para una web o API pública: un certificado público de ACM, en el que confían los navegadores (y que es gratuito con los servicios integrados).
  • Para cifrar datos en reposo o guardar claves de cifrado: KMS (Key Management Service) o CloudHSM.
  • Para guardar contraseñas o claves de API: Secrets Manager.

Modelo de precios

Se paga una cuota mensual por cada CA desde que se crea (menor en el modo de corta duración) y un precio por certificado emitido, más barato cuantos más se emiten al mes. Los certificados privados de ACM cuya clave no puedes extraer (los que usan ELB (Elastic Load Balancing), CloudFront o API Gateway) no se cobran; los que se exportan, sí.

Seguridad y alta disponibilidad

  • Las claves privadas de las CA se generan y quedan en HSM (Hardware Security Module: dispositivo físico que protege claves) gestionados por AWS; nunca salen.
  • Buenas prácticas: CA raíz en una cuenta propia con acceso mínimo y MFA (Multi-Factor Authentication: inicio de sesión con un segundo factor), y CA subordinadas en otras cuentas.
  • Políticas de IAM (Identity and Access Management) y de recurso para separar quién administra la CA y quién solo emite certificados.
  • CRL en un depósito de S3 aparte, accesible para quien deba comprobar revocaciones.
  • Registro de todas las operaciones en CloudTrail e informes de auditoría de los certificados emitidos.

Trampas de examen

  • "Certificados para servicios internos en los que solo confía la empresa": Private CA.
  • "Web pública con HTTPS": certificado público de ACM, no Private CA.
  • "Renovación automática de certificados privados en un balanceador": certificado privado de ACM firmado por Private CA.
  • "Certificados que duran horas o días, sin revocación": modo de corta duración.
  • "Una CA central para todas las cuentas": compartirla con RAM.
  • "Comprobar si un certificado está revocado": CRL u OCSP.
