AWS Fault Injection Service

AWS Fault Injection Service (AWS FIS)

En una frase: Provoca fallos controlados en tus recursos para probar cómo resiste la aplicación
Categoría: Administración y gobernanza (Management and Governance)
Certificaciones: SAP-C03
Documentación oficial: Documentación de AWS Fault Injection Service ↗

Qué es

AWS Fault Injection Service (antes Fault Injection Simulator) es el servicio de ingeniería del caos de AWS. Ejecuta experimentos que provocan fallos de verdad sobre recursos reales (parar instancias, añadir latencia, cortar la red, simular la caída de una zona) para ver cómo responde la aplicación y si se recupera como se espera. Incluye controles para hacerlo con seguridad, incluso en producción: si algo se tuerce, el experimento se detiene solo.

Conceptos clave

  • Plantilla de experimento: el plano del experimento, con sus acciones, objetivos, condiciones de parada y el rol de IAM (Identity and Access Management) que usa FIS. Cada ejecución de una plantilla es un experimento.
  • Acciones: lo que FIS hace a un recurso durante un tiempo: parar o reiniciar instancias EC2 (Elastic Compute Cloud), estresar CPU (Central Processing Unit: procesador) o memoria con Systems Manager, inyectar errores o limitación (throttling) en las llamadas a la API (Application Programming Interface: interfaz para que los programas se comuniquen) de un rol, cortar la conectividad de una subred, hacer conmutar una base de datos, y acciones para ECS (Elastic Container Service), EKS (Elastic Kubernetes Service), Lambda o EBS (Elastic Block Store). Pueden ir en serie o en paralelo.
  • Objetivos (targets): los recursos afectados, elegidos por ARN (Amazon Resource Name: identificador único de un recurso de AWS), por etiquetas o por filtros, todos o solo una parte (un número o un porcentaje), para limitar el radio de impacto.
  • Condiciones de parada: alarmas de CloudWatch; si una salta, FIS detiene el experimento.
  • Rol del experimento: rol de IAM que FIS asume para actuar; sin el permiso de una acción, esa acción falla.
  • Biblioteca de escenarios: plantillas listas para fallos complejos, como AZ (Availability Zone: zona de disponibilidad): Power Interruption (pérdida total de una zona), Cross-Region: Connectivity (corte entre regiones) o fallos parciales y difíciles de detectar (gray failures), como la lentitud de una zona.
  • Experimentos multicuenta: desde una cuenta orquestadora se actúa sobre recursos de varias cuentas de destino de la misma región, con encadenamiento de roles; las cuentas afectadas lo ven en su panel de AWS Health.
  • Registros e informes: la actividad del experimento puede ir a CloudWatch Logs o S3 (Simple Storage Service), y las llamadas que hace FIS quedan en CloudTrail.

Casos de uso típicos

  • Comprobar que una arquitectura multi-AZ aguanta la pérdida de una zona y medir cuánto tarda en recuperarse.
  • Validar un plan de recuperación ante desastres entre regiones cortando la conectividad entre ellas.
  • Probar reintentos con espera exponencial e interruptores (circuit breakers) inyectando errores y limitación en las API.
  • Jornadas de juego (game days) periódicas y experimentos dentro de la canalización de CI/CD (Continuous Integration / Continuous Delivery: integración y entrega continuas) antes de pasar a producción.
  • Comprobar que las alarmas y los procedimientos de respuesta a incidentes saltan de verdad.

Cuándo NO usarlo

  • Para evaluar si una aplicación cumple sus objetivos de RTO (Recovery Time Objective: cuánto tiempo puedes estar sin servicio) y RPO (Recovery Point Objective: cuántos datos puedes permitirte perder) sin romper nada: Resilience Hub (que, eso sí, puede recomendar experimentos de FIS).
  • Para pruebas de carga o rendimiento: herramientas de carga (FIS puede añadir estrés, pero no genera tráfico de usuarios).
  • Para conmutar de verdad el tráfico durante un incidente real: el desplazamiento de zona de Application Recovery Controller o Route 53.

Modelo de precios

Se paga por minuto de acción, desde que empieza hasta que acaba, multiplicado por el número de cuentas de destino del experimento. No hay coste por las plantillas.

Seguridad y alta disponibilidad

  • FIS hace acciones reales: AWS recomienda planificar y probar primero en preproducción.
  • Mínimo privilegio en el rol del experimento y objetivos acotados por etiquetas o porcentaje.
  • Condiciones de parada con alarmas de CloudWatch y parada manual en cualquier momento.
  • Permisos para crear y lanzar experimentos controlados con IAM (por ejemplo, solo el equipo de fiabilidad).
  • Auditoría con CloudTrail en todas las cuentas implicadas.

Trampas de examen

  • "Ingeniería del caos", "inyectar fallos", "game day": Fault Injection Service.
  • "Simular la caída de una zona de disponibilidad completa": escenario AZ: Power Interruption.
  • "Detener el experimento si suben los errores": condición de parada con una alarma de CloudWatch.
  • "Un solo experimento sobre una aplicación repartida en varias cuentas": experimento multicuenta desde una cuenta orquestadora.
  • "Probar la reacción ante limitación de la API": acción aws:fis:inject-api-throttle-error sobre el rol que hace las llamadas.
  • "Evaluar sin provocar fallos": Resilience Hub, no FIS.
