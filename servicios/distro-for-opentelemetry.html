AWS Distro for OpenTelemetry

AWS Distro for OpenTelemetry (ADOT)

En una frase: Recoge trazas y métricas con un estándar abierto y las envía a X-Ray o CloudWatch
Categoría: Herramientas para desarrolladores (Developer Tools)
Certificaciones: SAP-C03
Documentación oficial: Documentación de AWS Distro for OpenTelemetry ↗

Qué es

AWS Distro for OpenTelemetry es la distribución de OpenTelemetry que mantiene y da soporte AWS. OpenTelemetry es el estándar abierto de observabilidad para instrumentar aplicaciones (trazas, métricas y registros) sin atarse a un proveedor. Con ADOT instrumentas el código una sola vez y el recolector envía los datos a X-Ray, CloudWatch, Managed Service for Prometheus o herramientas de terceros, cambiando solo su configuración.

Conceptos clave

  • SDK (Software Development Kit: bibliotecas para programar contra AWS) y agentes de instrumentación: para lenguajes como Java, Python, JavaScript, .NET o Go; algunos instrumentan de forma automática (sin cambiar el código) las bibliotecas habituales y las llamadas a los SDK de AWS.
  • Recolector (collector): recibe, procesa y exporta la telemetría. Se compone de receptores (por ejemplo, de Prometheus), procesadores y exportadores (a X-Ray, CloudWatch o la escritura remota de Prometheus, firmando con SigV4).
  • Despliegue: como complemento (add-on) de EKS (Elastic Kubernetes Service) con el operador de ADOT, como contenedor auxiliar en tareas de ECS (Elastic Container Service), en instancias EC2 (Elastic Compute Cloud) o como capa de Lambda.
  • Soporte de AWS: componentes probados y con parches de seguridad, a diferencia de montar la distribución de la comunidad por tu cuenta.
  • Relación con X-Ray: los SDK y el demonio de X-Ray están en mantenimiento desde 2026 y la instrumentación recomendada para trazas es OpenTelemetry.

Casos de uso típicos

  • Trazas distribuidas de microservicios en EKS o ECS hacia X-Ray o CloudWatch Application Signals.
  • Recoger métricas con formato de Prometheus y enviarlas a Managed Service for Prometheus.
  • Estrategia multinube o con herramientas de terceros, sin reinstrumentar si se cambia de destino.
  • Instrumentar funciones Lambda con una capa sin tocar mucho el código.

Cuándo NO usarlo

  • Si basta con las métricas y los registros que los servicios ya envían a CloudWatch sin instrumentar.
  • Para métricas del sistema operativo y registros de instancias sin trazas: el agente de CloudWatch puede ser suficiente.
  • Para auditar llamadas a la API (Application Programming Interface: interfaz para que los programas se comuniquen) de AWS: CloudTrail.

Modelo de precios

ADOT es gratuito: se paga el cómputo donde corre el recolector y el servicio de destino (trazas de X-Ray, métricas y registros de CloudWatch, muestras de Prometheus…). Muestrear las trazas y filtrar métricas en el recolector reduce ese coste.

Seguridad y alta disponibilidad

  • El recolector usa roles de IAM (Identity and Access Management) (por ejemplo, de cuenta de servicio en EKS) con permisos mínimos de escritura en cada destino.
  • Envío firmado con SigV4 y cifrado en tránsito.
  • Filtrar en el recolector los datos sensibles antes de exportarlos.
  • Desplegar el recolector con réplicas para no perder telemetría si cae uno.

Trampas de examen

  • "Instrumentar con un estándar abierto, sin atarse a un proveedor": Distro for OpenTelemetry.
  • "Enviar las mismas trazas a X-Ray y a una herramienta de terceros": recolector de ADOT con dos exportadores.
  • "Métricas de Prometheus de EKS a Managed Service for Prometheus": recolector de ADOT (o el recolector gestionado).
  • "Instrumentar Lambda": capa de Lambda de ADOT.
