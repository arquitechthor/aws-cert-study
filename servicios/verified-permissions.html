Amazon Verified Permissions

En una frase: Autoriza acciones dentro de tus aplicaciones con políticas Cedar fuera del código
Categoría: Seguridad, identidad y cumplimiento (Security, Identity, and Compliance)
Certificaciones: SAP-C03
Documentación oficial: Documentación de Amazon Verified Permissions ↗

Qué es

Amazon Verified Permissions es un servicio de autorización fina para las aplicaciones que desarrollas tú. Saca la lógica de permisos del código: las reglas se escriben como políticas en el lenguaje Cedar (de código abierto), se guardan en el servicio y la aplicación pregunta en cada caso "¿puede este usuario hacer esta acción sobre este recurso?". Verified Permissions responde Allow o Deny. La autenticación (saber quién es el usuario) la hace otro, por ejemplo Cognito.

Conceptos clave

  • Almacén de políticas (policy store): el contenedor de las políticas y del esquema de una aplicación (o de un inquilino, en aplicaciones multiinquilino).
  • Esquema: describe los tipos de entidad (usuarios, grupos, documentos…), sus atributos y las acciones; las políticas se validan contra él.
  • Políticas Cedar: reglas permit o forbid sobre un principal, una acción y un recurso, con condiciones sobre atributos y contexto. Permiten modelos por roles (RBAC), por atributos (ABAC) o por relaciones. Un forbid que coincide gana siempre, y si nada coincide la respuesta es Deny.
  • Plantillas de política: una regla con huecos que se rellena por usuario o recurso (por ejemplo, "este usuario puede editar este documento" al compartirlo).
  • Fuente de identidad: un grupo de usuarios de Cognito u otro proveedor OIDC (OpenID Connect: estándar de identidad sobre OAuth 2.0). Con IsAuthorizedWithToken la aplicación envía el token JWT (JSON Web Token: token firmado con datos del usuario) y el servicio saca de él el principal y sus grupos.
  • Llamadas de autorización: IsAuthorized, IsAuthorizedWithToken y sus versiones por lotes para decidir varias cosas en una sola llamada (por ejemplo, qué botones mostrar).
  • Integración con API Gateway: puede crear el almacén a partir de una API (Application Programming Interface: interfaz para que los programas se comuniquen) y un autorizador de Lambda que protege sus rutas.

Casos de uso típicos

  • Permisos finos en una aplicación SaaS (Software as a Service: software que se usa como servicio): quién ve o edita cada documento, expediente o pedido.
  • Aislamiento entre inquilinos con un almacén de políticas por inquilino o reglas por atributo.
  • Cambiar reglas de negocio de acceso sin volver a desplegar el código.
  • Auditar decisiones de acceso y saber qué política las determinó.

Cuándo NO usarlo

  • Para permisos sobre recursos de AWS (quién puede borrar un depósito de S3 (Simple Storage Service)): IAM (Identity and Access Management).
  • Para el inicio de sesión y la gestión de usuarios de la aplicación: Cognito.
  • Para el acceso a la red o a aplicaciones internas completas: Verified Access.
  • Si la aplicación solo necesita "usuario conectado o no": la autenticación basta.

Modelo de precios

Se paga por petición de autorización (las peticiones por lotes cuentan como una, aunque decidan varias cosas) y por las peticiones de gestión de políticas. No hay mínimo.

Seguridad y alta disponibilidad

  • Validación de las políticas contra el esquema para evitar errores antes de aplicarlas.
  • Respuesta con las políticas que decidieron, para auditar; llamadas registradas en CloudTrail.
  • Validación de la firma y la caducidad de los tokens de la fuente de identidad.
  • Separar los almacenes por inquilino para aislarlos.

Trampas de examen

  • "Permisos finos dentro de la aplicación, fuera del código": Verified Permissions.
  • "Lenguaje Cedar": Verified Permissions (también lo usa Verified Access).
  • "Usuarios de Cognito y autorización por grupo y atributo": fuente de identidad de Cognito con IsAuthorizedWithToken.
  • "Decidir muchas cosas a la vez para pintar una pantalla": autorización por lotes.
  • "Permisos sobre recursos de AWS": IAM, no Verified Permissions.
