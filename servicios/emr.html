Amazon EMR

En una frase: Clústeres gestionados de Spark, Hive o Hadoop para procesar big data
Categoría: Análisis (Analytics)
Certificaciones: SAA-C03 SAP-C02 AIF-C01 CLF-C02
Documentación oficial: Documentación de Amazon EMR ↗

Qué es

Amazon EMR (Elastic MapReduce) es la plataforma gestionada de AWS para procesar grandes volúmenes de datos con marcos de código abierto: Apache Spark, Hive, Presto o Trino, Flink, HBase y el ecosistema de Hadoop. AWS se ocupa de aprovisionar, configurar y afinar el clúster; tú envías los trabajos. Es la opción natural para quien ya tiene cargas de Hadoop o Spark y quiere el control del entorno.

Conceptos clave

  • Tres formas de despliegue:
    • EMR en EC2 (Elastic Compute Cloud): clústeres de instancias; el máximo control.
    • EMR en EKS (Elastic Kubernetes Service): los trabajos de Spark se ejecutan en un clúster de Kubernetes compartido con otras aplicaciones.
    • EMR Serverless: sin clúster que gestionar; se paga por los recursos que usa cada trabajo y escala solo.
  • Tipos de nodo (en EC2):
    • Principal (primary): coordina el clúster.
    • Central (core): ejecuta tareas y guarda datos en HDFS (Hadoop Distributed File System: sistema de ficheros distribuido de Hadoop).
    • De tarea (task): solo cómputo, sin datos; es opcional y el candidato ideal para instancias Spot.
  • Almacenamiento: HDFS, en los discos del clúster, que desaparece con él; o EMRFS, que usa S3 (Simple Storage Service) como capa de datos y separa el cómputo del almacenamiento.
  • Clúster transitorio o de larga duración: el transitorio se crea, ejecuta sus pasos y se termina solo; el de larga duración queda encendido para uso interactivo.
  • Grupos o flotas de instancias: las flotas permiten mezclar varios tipos de instancia y capacidad bajo demanda y Spot, en varias AZ (Availability Zone: zona de disponibilidad).
  • Escalado gestionado: EMR ajusta el número de nodos según la carga, entre un mínimo y un máximo.
  • EMR Studio y cuadernos: entorno para desarrollar y depurar de forma interactiva.

Casos de uso típicos

  • Procesos de ETL (Extract, Transform, Load: extraer, transformar y cargar datos) y transformación de terabytes o petabytes con Spark.
  • Migrar un clúster de Hadoop local a la nube sin reescribir los trabajos.
  • Aprendizaje automático a gran escala con Spark MLlib y preparación de datos para entrenar modelos.
  • Análisis interactivo con Presto o Trino, y procesamiento de flujos con Flink o Spark Streaming.
  • Análisis de logs, clics y datos científicos (genómica).

Cuándo NO usarlo

  • ETL sin gestionar nada y con catálogo integrado: Glue.
  • Consultas SQL (Structured Query Language: lenguaje de consultas de bases de datos relacionales) puntuales sobre S3: Athena.
  • Almacén de datos para informes y BI (Business Intelligence: análisis de datos para el negocio): Redshift.
  • Flujos en tiempo real gestionados: Managed Service for Apache Flink o Data Firehose.
  • Cargas pequeñas u ocasionales: el clúster sale caro frente a las opciones sin servidor.

Modelo de precios

En EC2 se paga un cargo de EMR por instancia y segundo, sumado al precio de la instancia de EC2 y de sus volúmenes; admite Spot, instancias reservadas y Savings Plans. En EKS, un cargo por la vCPU y la memoria de los trabajos. En EMR Serverless, por la vCPU, la memoria y el almacenamiento que usan los trabajadores mientras se ejecutan.

Seguridad y alta disponibilidad

  • El clúster se lanza en tu VPC (Virtual Private Cloud), preferiblemente en subredes privadas, con grupos de seguridad gestionados.
  • Configuraciones de seguridad: cifrado en reposo (S3, discos locales) y en tránsito, y autenticación con Kerberos.
  • Roles de IAM (Identity and Access Management) para el servicio y para las instancias; con Lake Formation se aplican permisos por tabla, columna y fila.
  • Para alta disponibilidad, tres nodos principales. Guardar los datos en S3 (EMRFS) evita perderlos si el clúster cae.
  • Un clúster vive en una AZ; las flotas de instancias eligen la mejor AZ al lanzarlo.

Trampas de examen

  • "Hadoop", "Spark", "Hive" o "big data con marcos de código abierto": EMR.
  • "Migrar un clúster de Hadoop local con los mínimos cambios": EMR.
  • "Reducir el coste de un clúster de EMR": instancias Spot en los nodos de tarea (nunca dependas de Spot para el nodo principal ni para los nodos centrales con datos en HDFS).
  • "Los datos deben sobrevivir al clúster": S3 con EMRFS, no HDFS.
  • "Sin administrar clústeres": EMR Serverless; si además piden ETL sencillo, Glue.
  • "Consultas SQL ocasionales sobre S3": Athena, no EMR.
