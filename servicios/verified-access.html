AWS Verified Access

En una frase: Da acceso a apps internas sin VPN (Virtual Private Network: red privada virtual), comprobando identidad y dispositivo en cada petición
Categoría: Seguridad, identidad y cumplimiento (Security, Identity, and Compliance)
Certificaciones: SAP-C03
Documentación oficial: Documentación de AWS Verified Access ↗

Qué es

AWS Verified Access da acceso a aplicaciones internas sin VPN. En lugar de abrir la red entera una vez conectado, evalúa cada petición a cada aplicación con políticas que combinan la identidad del usuario (de IAM Identity Center o de un proveedor OIDC (OpenID Connect: estándar de identidad sobre OAuth 2.0)) y, si se quiere, el estado de seguridad de su dispositivo. Es la aplicación en AWS del modelo de confianza cero: nadie es de fiar solo por estar "dentro" de la red.

Conceptos clave

  • Instancia de Verified Access: el componente que evalúa las peticiones y deja pasar solo las que cumplen las políticas.
  • Proveedores de confianza: uno de identidad de usuario (IAM Identity Center o un proveedor compatible con OIDC) y, opcionalmente, varios de estado del dispositivo (soluciones de gestión o seguridad de equipos como CrowdStrike o Jamf).
  • Datos de confianza: lo que esos proveedores envían en cada petición: correo, grupos, puntuación de riesgo del equipo…
  • Grupos: conjuntos de aplicaciones con requisitos parecidos (por ejemplo, todas las de ventas), con una política de grupo que heredan.
  • Puntos de enlace: cada aplicación, detrás de un balanceador (ALB (Application Load Balancer: balanceador HTTP/HTTPS) o NLB (Network Load Balancer: balanceador TCP/UDP)) o de una interfaz de red, con su política opcional más estricta.
  • Políticas: se escriben en el lenguaje Cedar (por ejemplo, "solo el grupo Finanzas, desde equipos con el agente de seguridad y riesgo bajo").
  • Registros: todos los intentos de acceso, permitidos o denegados, a CloudWatch Logs, S3 (Simple Storage Service) o Data Firehose.

Casos de uso típicos

  • Sustituir la VPN corporativa para el acceso a aplicaciones web internas.
  • Dar a contratistas acceso a una sola aplicación, no a la red.
  • Exigir equipos gestionados y sanos para aplicaciones sensibles.
  • Auditar quién accedió a qué aplicación y desde qué dispositivo.

Cuándo NO usarlo

  • Para dar a un usuario acceso de red completo a una VPC (Virtual Private Cloud) (administración, protocolos variados): Client VPN.
  • Para unir una oficina o un centro de datos con AWS: Site-to-Site VPN o Direct Connect.
  • Para entrar en la consola de una instancia sin abrir puertos: Session Manager de Systems Manager.
  • Para autorizar acciones dentro de tu propia aplicación (quién puede ver qué factura): Verified Permissions.

Modelo de precios

Se paga por hora de cada aplicación (punto de enlace) asociada a Verified Access y por los GB procesados.

Seguridad y alta disponibilidad

  • Evaluación continua de cada petición: dificulta que un atacante salte de una aplicación a otra.
  • Integración con WAF (Web Application Firewall) para filtrar ataques a las aplicaciones.
  • Certificados de ACM (AWS Certificate Manager) para los dominios de las aplicaciones.
  • Registros detallados para auditoría y respuesta a incidentes.

Trampas de examen

  • "Acceso a aplicaciones internas sin VPN" o "confianza cero": Verified Access.
  • "Comprobar también el estado del dispositivo": proveedor de confianza de dispositivo.
  • "Las mismas reglas para todas las aplicaciones de un departamento": grupo con política común.
  • "Acceso de red completo para administradores": Client VPN.
  • "Autorización fina dentro de la aplicación": Verified Permissions, no Verified Access.
