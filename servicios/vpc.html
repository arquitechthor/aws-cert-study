Amazon VPC

Amazon Virtual Private Cloud (Amazon VPC)

Categoría: Redes y entrega de contenido (Networking and Content Delivery)
Certificaciones: SAA-C03 SAP-C02 AIF-C01 CLF-C02 DVA-C02

Qué es

Amazon VPC (Virtual Private Cloud) es una red virtual lógicamente aislada dentro de una región de AWS. Tú decides el rango de direcciones IP (Internet Protocol: dirección de red), cómo se divide en subredes, qué rutas existen y qué tráfico se permite. Casi todo lo que tiene una interfaz de red (EC2 (Elastic Compute Cloud), RDS (Relational Database Service), Lambda conectada a VPC, balanceadores, contenedores) vive dentro de una VPC. Cada región trae una VPC por defecto con subredes públicas para empezar rápido.

Conceptos clave

  • Bloque CIDR (Classless Inter-Domain Routing: notación de rangos de IP como 10.0.0.0/16): rango IPv4 (Internet Protocol version 4: direcciones IP de 32 bits) de la VPC, de /16 a /28, ampliable con bloques secundarios; opcionalmente también IPv6 (Internet Protocol version 6: direcciones IP de 128 bits).
  • Subred: parte del rango de la VPC que vive en una sola zona de disponibilidad. AWS reserva 5 direcciones de cada subred.
  • Subred pública vs privada: es pública si su tabla de rutas envía 0.0.0.0/0 a un internet gateway. Las privadas no tienen esa ruta.
  • NAT gateway (Network Address Translation: traducción de direcciones de red): permite que las instancias de subredes privadas salgan a internet (por ejemplo, para actualizaciones) sin aceptar conexiones entrantes. Es por zona: para alta disponibilidad, uno en cada zona. Para IPv6, el equivalente es el egress-only internet gateway.
  • Security groups: firewall con estado en la interfaz de red; solo reglas de permitir; pueden referenciar otros security groups.
  • Network ACL (Access Control List: lista de control de acceso): firewall sin estado a nivel de subred; reglas de permitir y denegar numeradas; hay que abrir también el tráfico de retorno (puertos efímeros). Útil para bloquear una IP concreta.
  • VPC endpoints: acceso privado a servicios de AWS sin pasar por internet. Los de tipo gateway (solo S3 (Simple Storage Service) y DynamoDB) son gratuitos y funcionan con rutas; los de tipo interface (PrivateLink) crean una interfaz de red con IP privada y tienen coste.
  • VPC peering: une dos VPC (incluso de otras cuentas o regiones) de forma privada. No es transitivo y los rangos no pueden solaparse.
  • Transit Gateway: concentrador que conecta muchas VPC y redes locales en estrella, con tablas de rutas propias.
  • Conectividad híbrida: Site-to-Site VPN (Virtual Private Network: red privada virtual) (túneles IPsec (Internet Protocol Security: cifrado de los paquetes IP en una VPN) por internet, rápida de montar) y Direct Connect (enlace dedicado, latencia estable).
  • VPC Flow Logs: registran metadatos del tráfico IP (origen, destino, puertos, aceptado o rechazado) hacia CloudWatch Logs, S3 o Firehose. No capturan el contenido de los paquetes.

Casos de uso típicos

  • Arquitectura de tres capas: balanceador en subredes públicas, aplicación y base de datos en subredes privadas.
  • Aislar entornos (producción, pruebas) o equipos en VPC distintas.
  • Extender el centro de datos a AWS con VPN o Direct Connect.
  • Acceso privado a S3 y DynamoDB desde subredes sin salida a internet.
  • Auditar tráfico y detectar conexiones rechazadas con Flow Logs.

Cuándo NO usarlo

  • Para inspeccionar el contenido del tráfico o filtrar por dominio: Network Firewall o appliances de terceros con Gateway Load Balancer, no solo security groups y NACL (Network Access Control List: firewall a nivel de subred).
  • Para conectar decenas de VPC entre sí: Transit Gateway o Cloud WAN (Wide Area Network: red de área extensa), no una malla de peerings.
  • Para exponer un servicio concreto a otras cuentas sin unir las redes: PrivateLink (servicio de endpoint), no peering.

A fondo: temas avanzados

Esta es la parte ampliada de la guía, con el nivel de detalle que piden los escenarios de redes de SAP-C02: direcciones sin solapes en muchas cuentas, VPC compartidas, topologías en estrella con salida e inspección centralizadas, endpoints y DNS (Domain Name System: traduce nombres de dominio a direcciones IP) a escala, y cómo elegir entre las formas de conectar redes.

Direcciones IP a escala

  • Sin solapes desde el principio: si dos rangos se solapan, no se pueden unir por peering ni enrutar por Transit Gateway. Rehacer el direccionamiento de una VPC en producción es caro, así que se planifica para todas las cuentas, regiones y redes locales a la vez.
  • VPC IPAM (IP Address Manager: planifica y reparte rangos de IP entre cuentas y regiones): reparte el espacio en grupos (pools) por región y entorno, se comparte con RAM (Resource Access Manager) a las cuentas de la organización, asigna rangos automáticamente al crear una VPC y avisa de solapes y de rangos sin usar.
  • Si el solape ya existe (por ejemplo, tras una adquisición): PrivateLink, que expone un servicio concreto sin unir las redes, o un NAT gateway privado que traduce a un rango que no se solapa.
  • Cuando faltan direcciones: se añaden bloques CIDR secundarios, por ejemplo del rango 100.64.0.0/10 para los pods de EKS (Elastic Kubernetes Service), sin tocar las subredes existentes.
  • Cuotas que deciden el diseño: 5 VPC por región (ampliable a cientos), 5 bloques IPv4 por VPC (hasta 50), 200 subredes por VPC y 50 peerings activos por VPC (hasta 125). Más de unas decenas de VPC conectadas entre sí ya apunta a Transit Gateway.

VPC compartidas (VPC sharing)

Una cuenta de red es dueña de la VPC y comparte subredes con RAM a otras cuentas u OU (Organizational Unit: unidad organizativa de AWS Organizations) de la misma organización; esas cuentas participantes lanzan sus recursos en las subredes compartidas.

  • La cuenta propietaria controla la VPC, las subredes, las tablas de rutas, las NACL, los gateways y los NAT gateways.
  • Los participantes gestionan solo sus recursos y sus security groups: no pueden tocar rutas, NACL ni gateways, no ven los recursos de otros participantes y no pueden usar el security group por defecto (es del propietario). Cada cuenta paga sus propios recursos.
  • Requisitos: todas las cuentas en la misma organización y el uso compartido de RAM activado desde la cuenta de administración. Las subredes de la VPC por defecto no se pueden compartir.
  • Ventajas: menos VPC, menos adjuntos de Transit Gateway y menos direcciones desperdiciadas, con la red en manos de un equipo central y los equipos de aplicación separados por cuenta. Compromiso: las cuotas de la VPC y el radio de fallo se comparten.

Topología en estrella con Transit Gateway

  • Segmentación con tablas de rutas: cada adjunto se asocia a una tabla (por dónde busca rutas) y propaga sus rutas a otras. Con tablas separadas, producción y desarrollo comparten el mismo Transit Gateway sin verse.
  • Salida a internet centralizada: una VPC de salida con NAT gateways por zona y, en las VPC de aplicación, la ruta 0.0.0.0/0 hacia el Transit Gateway. Ahorra NAT gateways, pero cada GB paga además el procesamiento del Transit Gateway: con mucho tráfico puede salir más caro que un NAT por VPC.
  • Inspección centralizada: una VPC de inspección con Network Firewall o con appliances detrás de un GWLB. En su adjunto hay que activar el modo appliance (appliance mode) para que la ida y la vuelta de cada flujo pasen por el mismo appliance; sin él, el tráfico entre zonas distintas puede volver por otro camino y el firewall con estado lo descarta.
  • Security groups entre VPC: por peering se puede referenciar un security group de la otra VPC si están en la misma región; por Transit Gateway también, en la misma región, activando la opción en el Transit Gateway (viene desactivada) y en el adjunto.
  • MTU (Maximum Transmission Unit: tamaño máximo de paquete en una red): dentro de una VPC se admiten tramas grandes de 9001 bytes; a través de Transit Gateway el máximo es 8500 y por VPN o internet, 1500. Un fallo que solo aparece con paquetes grandes suele ser esto.
  • Varias regiones: peering entre Transit Gateways (con rutas estáticas) o Cloud WAN, que define la red global y su segmentación con una política central.

Endpoints a escala

  • Endpoints de tipo interface centralizados: en una VPC de servicios compartidos, con el DNS privado del endpoint desactivado y una zona alojada privada de Route 53 por servicio (sqs.<región>.amazonaws.com) asociada a todas las VPC de aplicación. Se paga un endpoint en vez de uno por VPC, a cambio del tráfico por el Transit Gateway.
  • Los endpoints de tipo gateway solo sirven dentro de su VPC: no se alcanzan desde otra VPC (peering o Transit Gateway), ni desde una VPN o Direct Connect. Para llegar a S3 de forma privada desde la red local hace falta el endpoint de S3 de tipo interface.
  • Políticas de endpoint como perímetro de datos: con aws:ResourceOrgID el endpoint solo deja llegar a buckets de la propia organización, lo que corta la exfiltración a cuentas ajenas.

DNS híbrido

  • El resolvedor de cada VPC (la dirección .2 del rango) solo responde a consultas que nacen dentro de la VPC.
  • Endpoint de entrada de Route 53 Resolver: la red local resuelve las zonas privadas de AWS. Endpoint de salida con reglas de reenvío: las VPC resuelven los dominios de la red local.
  • Basta un juego de endpoints, en varias zonas, en la VPC de servicios compartidos: las reglas de reenvío se comparten con RAM al resto de cuentas y VPC.

Modelo de precios

Crear una VPC, subredes, tablas de rutas, security groups y NACL no cuesta nada. Se paga por los componentes gestionados: NAT gateways (por hora y por GB procesado), endpoints de tipo interface, conexiones VPN, Transit Gateway (por adjunto y por GB), direcciones IPv4 públicas, Flow Logs (según el destino) y la transferencia de datos entre zonas o regiones. Los endpoints gateway de S3 y DynamoDB son gratuitos y además ahorran tráfico por el NAT.

Seguridad y alta disponibilidad

  • Defensa en capas: NACL en la subred y security groups en cada recurso.
  • Recursos sensibles en subredes privadas; solo balanceadores en las públicas.
  • Subredes en al menos dos zonas, y un NAT gateway por zona para no depender de una sola.
  • Políticas en los endpoints de VPC para limitar a qué buckets o recursos se accede.
  • VPC Block Public Access para impedir de forma centralizada el tráfico de internet en VPC que no deben tenerlo.

Trampas de examen

  • "Instancias privadas deben descargar parches de internet": NAT gateway en una subred pública.
  • "Acceder a S3 sin pasar por internet y sin coste": endpoint de VPC de tipo gateway.
  • "Bloquear una IP maliciosa concreta": regla de denegar en la NACL (los security groups no deniegan).
  • "A conecta con B y B con C, pero A no llega a C": el peering no es transitivo; Transit Gateway.
  • "Muchas VPC y oficinas en estrella": Transit Gateway.
  • "Diagnosticar tráfico rechazado": VPC Flow Logs.
  • "Conexión dedicada con latencia constante": Direct Connect; "rápido y cifrado por internet": Site-to-Site VPN.
