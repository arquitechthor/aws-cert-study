AWS Resilience Hub

En una frase: Evalúa si tu aplicación cumple sus objetivos de RTO (Recovery Time Objective: cuánto tiempo puedes estar sin servicio) y RPO (Recovery Point Objective: cuántos datos puedes permitirte perder) y propone cómo mejorarla
Categoría: Administración y gobernanza (Management and Governance)
Certificaciones: SAP-C03
Documentación oficial: Documentación de AWS Resilience Hub ↗

Qué es

AWS Resilience Hub es el sitio central para gestionar y mejorar la resiliencia de tus aplicaciones en AWS. Defines los objetivos de recuperación de cada aplicación (RTO y RPO), el servicio evalúa su arquitectura real frente a ellos siguiendo el marco Well-Architected y te dice qué cambiar para cumplirlos. También propone alarmas, procedimientos operativos y experimentos de Fault Injection Service para comprobar que la recuperación funciona de verdad.

Conceptos clave

  • Aplicación: el conjunto de recursos que se evalúa juntos. Se describe a partir de pilas de CloudFormation, ficheros de estado de Terraform, grupos de recursos, aplicaciones de myApplications o AppRegistry, y opcionalmente espacios de nombres de clústeres de EKS (Elastic Kubernetes Service). Hay que publicarla antes de evaluarla.
  • Política de resiliencia: los objetivos de RTO y RPO que debe cumplir la aplicación para cuatro tipos de interrupción: fallo de la propia aplicación (un proceso o servicio de software), de la infraestructura (por ejemplo, una instancia), de una zona de disponibilidad y de una región. Varias aplicaciones pueden compartir política y la política no cambia nada en los recursos.
  • Evaluación: calcula el RTO y el RPO estimados de cada componente y de la aplicación, y dice si cumple la política. Da una puntuación de resiliencia según cuánto sigue la aplicación las recomendaciones.
  • Recomendaciones de resiliencia: cambios de arquitectura por componente (por ejemplo, multi-AZ en una base de datos, réplicas entre regiones, copias de seguridad), con sus compromisos de coste.
  • Recomendaciones operativas: alarmas de CloudWatch, SOP (Standard Operating Procedure: procedimiento operativo estándar, el paso a paso ante un incidente) (procedimientos operativos estándar, como documentos de Systems Manager) y experimentos de FIS para probar cada tipo de interrupción. Se pueden exportar como plantillas de CloudFormation.
  • Detección de deriva: evaluaciones diarias automáticas con aviso (por ejemplo, por SNS (Simple Notification Service)) si la aplicación deja de cumplir su política o si cambian sus recursos.

Casos de uso típicos

  • Comprobar, antes de pasar a producción, si una arquitectura cumple los RTO y RPO que exige el negocio.
  • Añadir una evaluación de resiliencia a la canalización de CI/CD (Continuous Integration / Continuous Delivery: integración y entrega continuas) y frenar el despliegue si empeora.
  • Vigilar de forma continua que los cambios no rompen los objetivos de recuperación.
  • Preparar alarmas, procedimientos y experimentos de caos coherentes con cada tipo de fallo.
  • Dar a auditores o clientes una prueba periódica de que se cumplen los objetivos acordados.

Cuándo NO usarlo

  • Para provocar fallos y ver qué pasa: Fault Injection Service (Resilience Hub lo recomienda y lo lanza, pero el que actúa es FIS).
  • Para hacer las copias o la recuperación: Backup o Elastic Disaster Recovery.
  • Para conmutar el tráfico durante un incidente real: Application Recovery Controller o Route 53.
  • Para revisar una carga contra todos los pilares del marco (seguridad, costes…), no solo la fiabilidad: Well-Architected Tool.

Modelo de precios

Se paga una tarifa mensual por cada aplicación que se evalúa, según el tiempo que está dada de alta. Los experimentos de FIS, las alarmas de CloudWatch y los demás servicios que uses se pagan aparte.

Seguridad y alta disponibilidad

  • Accede a los recursos con un rol de IAM (Identity and Access Management) que tú creas o eliges (permisos de solo lectura para la evaluación).
  • Puede evaluar aplicaciones con recursos en varias cuentas y regiones, mediante roles en cada cuenta.

Trampas de examen

  • "Comprobar si la aplicación cumple el RTO y el RPO" o "puntuación de resiliencia": Resilience Hub.
  • "Aviso cuando un cambio hace que deje de cumplir los objetivos": detección de deriva con evaluaciones diarias.
  • "Alarmas, procedimientos y experimentos recomendados": recomendaciones operativas de Resilience Hub (que se ejecutan con CloudWatch, Systems Manager y FIS).
  • "Inyectar fallos": FIS, no Resilience Hub.
  • "Evaluar en la canalización antes de desplegar": evaluación de Resilience Hub como paso de CodePipeline.
