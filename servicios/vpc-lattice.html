Amazon VPC Lattice

En una frase: Conecta y protege la comunicación entre servicios de varias cuentas sin gestionar redes
Categoría: Redes y entrega de contenido (Networking and Content Delivery)
Certificaciones: SAP-C03
Documentación oficial: Documentación de Amazon VPC Lattice ↗

Qué es

Amazon VPC Lattice es un servicio de red de aplicaciones totalmente gestionado. Sirve para que los microservicios y los recursos de una aplicación (APIs, bases de datos, puntos de enlace con nombre DNS (Domain Name System: traduce nombres de dominio a direcciones IP) o IP (Internet Protocol: dirección de red)) se encuentren y se hablen entre sí aunque estén repartidos en muchas VPC (Virtual Private Cloud) y cuentas, sin montar peering, tablas de rutas ni balanceadores intermedios. Cada petición puede autorizarse con una política de IAM (Identity and Access Management), y el servicio deja métricas y registros de todo el tráfico.

Conceptos clave

  • Servicio: una pieza de software que se despliega por separado (en EC2 (Elastic Compute Cloud), contenedores de ECS (Elastic Container Service) o EKS (Elastic Kubernetes Service), Fargate o funciones Lambda). Se define con agentes de escucha (protocolo y puerto), reglas (prioridad, condiciones y acciones) y grupos de destino.
  • Grupo de destino: los destinos que atienden el servicio: instancias EC2, direcciones IP, funciones Lambda, balanceadores ALB (Application Load Balancer: balanceador HTTP/HTTPS), tareas de ECS o pods de Kubernetes. Se parecen a los de ELB (Elastic Load Balancing), pero no son intercambiables.
  • Red de servicios (service network): el límite lógico que agrupa servicios y recursos. Los clientes de una VPC asociada a la red pueden llamar a los servicios de esa red si están autorizados.
  • Recursos, pasarela de recursos y configuración de recursos: para exponer algo que no es un servicio HTTP (una base de datos RDS (Relational Database Service), una IP, un nombre DNS), el dueño crea una resource gateway en su VPC y una resource configuration que lo representa, y la comparte con RAM (Resource Access Manager).
  • Políticas de autorización (auth policies): documentos de IAM asociados a la red de servicios (control grueso) o a cada servicio (control fino). Con el tipo de autenticación AWS_IAM, el cliente debe firmar cada petición con SigV4; para que pase, tanto la política de autorización como la de identidad del llamante deben permitirlo.
  • Directorio de servicios: registro central de los servicios propios o compartidos con la cuenta.
  • Funciones por rol: el dueño de la red (equipo de red o de plataforma) crea y comparte la red y fija el acceso general; el dueño del servicio (desarrollo) crea su servicio, sus reglas y su control de acceso fino.

Casos de uso típicos

  • Comunicación entre microservicios repartidos en decenas de cuentas de una organización, incluso con rangos CIDR (Classless Inter-Domain Routing: notación de rangos de IP como 10.0.0.0/16) solapados.
  • Seguridad de confianza cero entre servicios: cada llamada se autentica con la identidad de IAM del que llama, no por su IP.
  • Migración y modernización: enrutar por ruta o cabecera una parte del tráfico a la versión nueva (por ejemplo, de EC2 a Lambda o contenedores) con pesos en las reglas.
  • Compartir de forma privada una base de datos o un servicio de otra cuenta como recurso de la red.
  • Acceso desde el centro de datos a los servicios de la red mediante un punto de enlace de VPC de tipo service network a través de Direct Connect o VPN (Virtual Private Network: red privada virtual).

Cuándo NO usarlo

  • Para dar acceso desde internet a tu aplicación: un balanceador ALB o NLB (Network Load Balancer: balanceador TCP/UDP), API Gateway o CloudFront.
  • Para conectar redes enteras con enrutamiento IP general (todas las subredes entre sí, tráfico no ligado a un servicio concreto): Transit Gateway o Cloud WAN (Wide Area Network: red de área extensa).
  • Para publicar un único servicio a muchos consumidores externos tipo SaaS (Software as a Service: software que se usa como servicio), cuando basta un punto de enlace por consumidor: PrivateLink.
  • Si la aplicación necesita WebSocket de forma nativa: Lattice no lo admite directamente (solo con agentes de escucha TLS (Transport Layer Security: cifrado de las conexiones) o como recurso).

Dentro de un clúster, ECS Service Connect y las mallas de servicios hacen un papel parecido; Lattice lo extiende entre VPC y cuentas sin instalar intermediarios (sidecars) en cada tarea.

Modelo de precios

Tres dimensiones por servicio: las horas que el servicio está aprovisionado, los GB procesados (lo que recibe más lo que responde) y el número de peticiones HTTP (o de conexiones TCP (Transmission Control Protocol: protocolo de transporte fiable) con agentes de escucha TLS). Para recursos, el dueño de la red paga por hora cada configuración de recursos asociada y el consumidor, los datos que intercambia. No hay cargo aparte por el tráfico entre zonas de disponibilidad: va incluido en el de datos procesados.

Seguridad y alta disponibilidad

  • Defensa en capas: sin asociación de la VPC (o punto de enlace de tipo service network) no hay acceso; después, grupos de seguridad en la asociación de la VPC (hasta cinco); después, políticas de autorización en la red y en cada servicio.
  • Las políticas de autorización de la red no se aplican a las configuraciones de recursos.
  • Agentes de escucha HTTPS (HTTP Secure: HTTP cifrado con TLS) con certificado gestionado por Lattice (o propio con ACM (AWS Certificate Manager) y dominio personalizado), y agentes TLS que no terminan el cifrado (paso directo hasta el destino).
  • Afinidad de zona: el cliente recibe la IP de Lattice de su misma zona y, si cae, la de otra.
  • Registros de acceso a CloudWatch Logs, Data Firehose o S3 (Simple Storage Service), y métricas por petición en CloudWatch.
  • Compartición entre cuentas de redes, servicios y recursos con RAM.

Trampas de examen

  • "Microservicios en muchas cuentas, CIDR solapados, mínima gestión de red": VPC Lattice, no peering ni Transit Gateway.
  • "Autorizar cada llamada entre servicios con IAM": política de autorización con AWS_IAM; el cliente firma con SigV4 (si no firma, recibe 403).
  • "La aplicación debe descifrar ella misma el tráfico": agente de escucha TLS (paso directo), no HTTPS.
  • "Acceso desde el centro de datos": punto de enlace de VPC de tipo service network por Direct Connect o VPN.
  • "Compartir una base de datos RDS de otra cuenta": pasarela y configuración de recursos compartidas con RAM.
  • "Probar la versión nueva con el 10 % del tráfico": reglas con grupos de destino ponderados.
