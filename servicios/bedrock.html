Amazon Bedrock

★ Servicio clave Guía ampliada con temas avanzados y preguntas difíciles en el cuestionario.

En una frase: Acceso por API a modelos fundacionales de varias empresas para crear apps de IA
Categoría: Machine learning (Machine Learning)
Certificaciones: SAP-C03 AIF-C01 DVA-C03
Documentación oficial: Documentación de Amazon Bedrock ↗

Qué es

Amazon Bedrock es un servicio totalmente gestionado y serverless que da acceso por API (Application Programming Interface: interfaz para que los programas se comuniquen) a modelos fundacionales (FM) de varios proveedores (Amazon Nova, Anthropic Claude, Meta Llama, Mistral y otros). No hay infraestructura que gestionar. Además de invocar modelos, ofrece herramientas para personalizarlos, conectarlos con tus datos (RAG), añadir salvaguardas y evaluarlos.

Conceptos clave

  • Invocación: APIs InvokeModel (formato de cada proveedor) y Converse (interfaz unificada para conversaciones y uso de herramientas), con respuesta en streaming.
  • Parámetros de inferencia: temperatura y top-p (más altos, más creatividad y variación; más bajos, más determinismo), máximo de tokens de salida y secuencias de parada. Se cobra por tokens de entrada y de salida.
  • Knowledge Bases: RAG gestionado. Toma documentos (por ejemplo, de S3 (Simple Storage Service)), los divide, genera embeddings, los guarda en un almacén vectorial y recupera los fragmentos relevantes para fundamentar la respuesta.
  • Agents: descomponen una tarea en pasos y llaman a APIs o funciones Lambda (grupos de acciones) y a bases de conocimiento.
  • Guardrails: filtros de contenido dañino, temas denegados, palabras bloqueadas, detección y enmascarado de datos personales, comprobaciones de fundamentación contextual (contra alucinaciones) y de razonamiento automatizado. Se aplican a la entrada y a la salida.
  • Personalización de modelos: fine-tuning con datos etiquetados, continued pre-training con datos sin etiquetar del dominio y destilación (un modelo pequeño aprende de uno grande).
  • Evaluación de modelos: automática (métricas o un modelo como juez) o humana.
  • Inferencia entre regiones: perfiles de inferencia que reparten las peticiones entre regiones de una geografía o globalmente, para ganar capacidad.
  • Opciones de consumo: bajo demanda (con niveles Standard, Priority y Flex), por lotes (más barato, asíncrono) y Provisioned Throughput (capacidad reservada, necesaria típicamente para modelos personalizados).

Comandos de ejemplo

Se necesita la AWS CLI (Command Line Interface: línea de comandos) configurada con un rol que tenga permiso sobre el modelo. Los identificadores son de ejemplo (KB12345678 es una base de conocimiento inventada y 111122223333 la cuenta ficticia que usa AWS). Los comandos están escritos para bash; en PowerShell, el JSON (JavaScript Object Notation: formato de datos en texto) entre comillas da problemas, así que es más cómodo guardarlo en un fichero y pasarlo con file://peticion.json.

Ver qué modelos y perfiles de inferencia hay en la región

aws bedrock list-foundation-models --by-provider anthropic \
  --query 'modelSummaries[].modelId' --output table

# Perfiles entre regiones (eu., us., global.…)
aws bedrock list-inference-profiles --type-equals SYSTEM_DEFINED \
  --query 'inferenceProfileSummaries[].inferenceProfileId' --output table

Preguntar a un modelo con Converse

aws bedrock-runtime converse \
  --model-id eu.amazon.nova-lite-v1:0 \
  --messages '[{"role":"user","content":[{"text":"Resume en una frase qué es Amazon SQS."}]}]' \
  --inference-config '{"maxTokens":300,"temperature":0.2}' \
  --query 'output.message.content[0].text' --output text
  • converse usa el mismo formato con todos los modelos; invoke-model exige el formato propio de cada proveedor.
  • Como --model-id sirve un modelo o un perfil de inferencia (el prefijo eu. reparte las peticiones entre regiones europeas). Muchos modelos recientes solo se pueden invocar a través de un perfil.
  • Sin --query, la respuesta incluye usage con los tokens de entrada y de salida, útil para estimar el coste.
  • Para exigir un guardrail, se añade --guardrail-config '{"guardrailIdentifier":"<id>","guardrailVersion":"1"}'.

Consultar una base de conocimiento (RAG)

aws bedrock-agent-runtime retrieve-and-generate \
  --input '{"text":"¿Cuántos días de vacaciones hay?"}' \
  --retrieve-and-generate-configuration '{
    "type": "KNOWLEDGE_BASE",
    "knowledgeBaseConfiguration": {
      "knowledgeBaseId": "KB12345678",
      "modelArn": "arn:aws:bedrock:eu-west-1:111122223333:inference-profile/eu.amazon.nova-lite-v1:0"
    }
  }'
  • retrieve-and-generate busca los fragmentos y genera la respuesta con sus citas; retrieve solo devuelve los fragmentos, para montar tú el prompt.
  • Las bases de conocimiento y los agentes van por bedrock-agent-runtime; la inferencia directa, por bedrock-runtime; y la gestión (crear, listar), por bedrock y bedrock-agent.
  • Tras cambiar documentos en el origen hay que sincronizar: aws bedrock-agent start-ingestion-job --knowledge-base-id KB12345678 --data-source-id <id>.

Casos de uso típicos

  • Asistentes y chatbots que responden con la documentación de la empresa (RAG).
  • Resumir, clasificar o extraer información de textos y documentos.
  • Generar contenido: textos, código, imágenes.
  • Agentes que ejecutan tareas de varios pasos llamando a sistemas internos.
  • Generar preguntas de repaso o materiales de estudio a partir de apuntes.

Cuándo NO usarlo

  • Si necesitas entrenar desde cero un modelo propio o usar ML (Machine Learning: aprendizaje automático) clásico (regresión, clasificación tabular): SageMaker AI.
  • Si quieres un asistente listo para usar sin desarrollar nada: Amazon Q.
  • Tareas que resuelve un servicio de IA (inteligencia artificial) específico con menos coste y más precisión: Textract (extraer texto de documentos), Comprehend (sentimiento, entidades), Transcribe, Translate, Rekognition…
  • Para ejecutar agentes en producción con memoria, identidad y herramientas gestionadas a escala existe un servicio específico: Amazon Bedrock AgentCore.

A fondo: temas avanzados

La parte ampliada de la guía, con el nivel de los escenarios de SAP-C03 y de un uso real en una empresa: por qué llegan errores de limitación aunque se consuma poco, cómo se reparten las peticiones entre regiones sin saltarse la residencia de los datos, cómo se gobierna Bedrock en muchas cuentas, cómo se diseña un RAG serio y qué opción de consumo sale más barata en cada caso.

Cuotas, tokens y errores de limitación

  • En bajo demanda, las cuotas son por modelo y por región: tokens por minuto y peticiones por minuto, además de un tope diario de tokens por cuenta. Al superarlas llega ThrottlingException y hay que reintentar con espera exponencial y algo de aleatoriedad.
  • La trampa de max_tokens: al llegar la petición, Bedrock aparta de la cuota los tokens de entrada más el máximo de salida pedido, y devuelve lo que sobra mientras genera. Con un max_tokens muy alto, unas pocas peticiones simultáneas agotan la cuota aunque las respuestas reales sean cortas. Ajustarlo al tamaño real de las respuestas es la primera medida.
  • En muchos modelos (por ejemplo, los de Anthropic) cada token de salida descuenta varias veces de la cuota; la ficha de cada modelo indica cuántas. Los tokens leídos de la caché de prompts no cuentan.
  • Para ganar capacidad: inferencia entre regiones, el nivel Priority, Provisioned Throughput o pedir un aumento de cuota. Para quitar carga del tiempo real: inferencia por lotes, el nivel Flex y la caché de prompts.
  • Las métricas de CloudWatch del espacio AWS/Bedrock (invocaciones, latencia, tokens de entrada y salida, limitaciones) permiten vigilar cuánto falta para la cuota.

Inferencia entre regiones y residencia de los datos

OpciónDónde se procesaCuándo elegirla
Modelo en la propia regiónSolo en esa regiónNormativa estricta de una sola región, si el modelo lo permite (muchos recientes solo admiten perfiles)
Perfil geográfico (eu., us., apac.…)Cualquier región de destino de esa geografíaMás capacidad manteniendo los datos dentro de la Unión Europea, de Estados Unidos, etc.
Perfil global (global.)Cualquier región comercial con capacidadLa máxima capacidad cuando no hay requisitos de residencia
  • Permisos: el rol necesita bedrock:InvokeModel sobre el perfil y sobre el modelo en las regiones de destino (en el perfil global, sobre el recurso del modelo sin región). Si falta lo segundo, la llamada falla aunque el perfil esté permitido.
  • SCP (Service Control Policy: límite de permisos para las cuentas de una organización) que bloquean regiones: si una SCP solo permite la región de origen, el perfil geográfico falla al enrutar hacia otra región de destino. Hay que permitir todas las regiones de destino del perfil o añadir a la SCP la excepción para perfiles de inferencia que documenta AWS.

Gobierno en una organización con muchas cuentas

  • Qué modelos se pueden usar: los modelos sin servidor están disponibles por defecto, así que el control se hace con IAM y con SCP que deniegan bedrock:InvokeModel* y bedrock:Converse* sobre los modelos no aprobados. Los de Anthropic piden además un formulario de uso una sola vez; enviado por API desde la cuenta de administración, vale para toda la organización.
  • Guardrails obligatorios, tres niveles:
    • La clave de condición bedrock:GuardrailIdentifier en una política deniega las llamadas que no indiquen el guardrail exigido. Funciona, pero la aplicación tiene que indicarlo.
    • Un guardrail por defecto de la cuenta se aplica a todas sus invocaciones.
    • Una política de Bedrock de Organizations, desde la cuenta de administración, aplica un guardrail a todas las invocaciones de las cuentas u OU (Organizational Unit: unidad organizativa de AWS Organizations) indicadas sin que la aplicación lo pida. Es una política declarativa, no una SCP: si hay varias en el árbol no se suman, se resuelve una política efectiva por cuenta según las reglas de herencia.
  • ApplyGuardrail evalúa un texto con un guardrail sin invocar ningún modelo: sirve para proteger también modelos que no están en Bedrock.
  • Repartir el coste por equipo, aplicación o cliente: perfiles de inferencia de aplicación con etiquetas de asignación de costes (también cuentan las etiquetas del rol o de la sesión). Las etiquetas hay que activarlas en Billing para que salgan en el CUR (Cost and Usage Report).
  • Auditoría: CloudTrail registra las llamadas, pero no el contenido. El registro de invocaciones (prompts y respuestas) está desactivado por defecto, se configura por región y solo escribe en CloudWatch Logs o S3 de la misma cuenta y región; para centralizarlo, se replica desde ahí a la cuenta de registro.

Acceso privado

  • Puntos de enlace de interfaz (PrivateLink) distintos para bedrock-runtime (inferencia), bedrock-agent-runtime (bases de conocimiento y agentes) y bedrock (gestión). Una aplicación de RAG necesita al menos los dos primeros.
  • La política del punto de enlace limita qué acciones y qué modelos se pueden usar desde la VPC, y la condición aws:SourceVpce en las políticas obliga a pasar por él.

Diseñar un RAG con Knowledge Bases

Almacén vectorialCuándo encaja
S3 VectorsMuchos vectores al menor coste, si se acepta algo más de latencia
OpenSearch ServerlessBaja latencia y búsqueda híbrida (palabras clave y significado); Bedrock puede crearlo por ti
Aurora PostgreSQL (pgvector)Ya se usa Aurora y se quieren los vectores junto a los datos relacionales
Neptune AnalyticsGraphRAG (generación aumentada por recuperación apoyada en un grafo de conocimiento): las relaciones entre entidades importan para responder
Pinecone, MongoDB Atlas, RedisLa empresa ya tiene uno de esos productos
  • Troceado: fijo, jerárquico (fragmentos pequeños para buscar y su bloque padre como contexto), semántico o sin trocear. Cambiarlo obliga a volver a ingerir los documentos.
  • Que cada usuario vea solo lo suyo: la base de conocimiento lee con su propio rol, así que los permisos del origen no se aplican a quien pregunta. Se añaden metadatos a cada documento (un fichero .metadata.json junto a él en S3, por ejemplo con el departamento) y la aplicación filtra por ellos en cada consulta según la identidad del usuario.
  • Calidad: búsqueda híbrida cuando el almacén la admite, un modelo de reordenación (reranking) sobre los resultados y la evaluación de bases de conocimiento para medir los cambios.
  • Datos al día: cada cambio en el origen necesita un trabajo de ingesta, que se puede programar con EventBridge Scheduler.

SituaciónOpción

Peticiones en tiempo real que toleran más latenciaNivel Flex
Latencia crítica en los picosNivel Priority (más caro)
Volumen alto y estable, o un modelo personalizadoProvisioned Throughput (sin compromiso, a 1 o a 6 meses)

Mezcla de preguntas sencillas y difícilesEnrutado inteligente de prompts entre dos modelos de la misma familia, o un modelo pequeño destilado

Modelo de precios

En bajo demanda se paga por tokens de entrada y de salida (o por imagen o segundo de vídeo), con precios distintos por modelo y por nivel de servicio. La inferencia por lotes es más barata. Provisioned Throughput se paga por hora según las unidades de modelo reservadas. Se cobran aparte la personalización (entrenamiento y almacenamiento del modelo), los Guardrails, las evaluaciones y los servicios asociados, como el almacén vectorial.

Seguridad y alta disponibilidad

  • Tus prompts y respuestas no se usan para entrenar los modelos base ni se comparten con los proveedores.
  • Cifrado en tránsito y en reposo (con claves de KMS (Key Management Service) para modelos personalizados y otros recursos).
  • Acceso privado desde la VPC (Virtual Private Cloud) con endpoints de interfaz (PrivateLink).
  • Permisos con IAM (Identity and Access Management) hasta el nivel de modelo; auditoría de llamadas con CloudTrail e invocaciones registrables en CloudWatch o S3.
  • IA responsable: Guardrails, evaluación de modelos y comprobación de sesgos y toxicidad.

Así lo uso en Kopi

Kopi usa Bedrock para generar preguntas de repaso a partir de los apuntes de la sección Conocimiento. Una función Lambda envía el texto al modelo Claude Haiku con InvokeModel, con un límite de tokens de salida, y devuelve las preguntas. El identificador del modelo está en una variable de entorno, así que se puede cambiar sin tocar código. Todo queda dentro de AWS, sin claves de API externas: el permiso es bedrock:InvokeModel en el rol de ejecución. Se eligió un modelo pequeño y rápido porque la tarea no necesita más y el coste por token es menor.

Así lo uso en Prompt Quest

En Prompt Quest (código público) Bedrock no decide cada jugada: compila la estrategia que cada jugador escribe en lenguaje natural a una política JSON, que después ejecuta un motor determinista. Es una llamada por estrategia en lugar de una por movimiento: sin latencia durante la partida y con partidas reproducibles.

  • Salida estructurada: la respuesta tiene que cumplir un JSON Schema con enumeraciones cerradas (hechos, acciones y objetivos del juego), y el código la vuelve a validar y acotar.
  • Prompt caching: el mensaje de sistema es largo e idéntico en todas las llamadas, así que lleva cache_control y las siguientes llamadas son más baratas y rápidas.
  • Modelo pequeño: Claude Haiku, con un tiempo máximo de 25 s y dos reintentos; el modelo se elige al desplegar.
  • Inyección de prompts: el texto del jugador va delimitado como dato no confiable, el modelo marca los intentos (injectionAttempt) y el vocabulario cerrado impide pedir ventajas imposibles.
  • Plan B: si Bedrock falla o se niega, un compilador heurístico toma el relevo.
  • Crónica sin inventos: al acabar la partida, el modelo escribe una crónica a partir de hechos extraídos por el código, no de la partida entera.

Trampas de examen

  • "Datos privados o actualizados sin reentrenar": RAG con Knowledge Bases, no fine-tuning.
  • "Respuestas más deterministas": bajar la temperatura.
  • "Bloquear temas" o "ocultar datos personales": Guardrails.
  • "Modelo personalizado en producción": Provisioned Throughput.
  • "Muchas peticiones sin urgencia al menor coste": inferencia por lotes.
  • "¿Se usan mis datos para entrenar el modelo?": no.
  • "Ejecutar varios pasos y llamar a APIs": Agents.
  • "Limitación aunque el consumo real es bajo": max_tokens demasiado alto.
  • "Más capacidad sin sacar los datos de la UE": perfil de inferencia geográfico eu., no el global.
  • "Guardrail en todas las cuentas aunque la aplicación no lo indique": política de Bedrock en Organizations; una SCP con bedrock:GuardrailIdentifier solo rechaza las llamadas sin él.
  • "Coste por cliente o por equipo": perfiles de inferencia de aplicación con etiquetas.
